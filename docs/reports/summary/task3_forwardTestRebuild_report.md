## 1. What was wrong with the old log, and why it is archived, not deleted

`output/summary/forward_test_log.csv` (2,088 rows) was generated by `src/forward_test.py` for:
58 items (the old Type-level pilot scope), 6 individual models (Naive/MA3/MA6/MA12/Croston/SBA)
scored separately, on `output/data/processed_pilot_sales_monthly.csv` — which is `createDate`-
keyed. All three of these are now wrong simultaneously:

- **Scope**: the project's current scope is 128 items across 8 Types / 2 Categories
  (`output/summary/part1_category_scope_all_codes.csv`, confirmed by direct read: 68 Fuse + 60
  Surge Arrester = 128, 8 distinct Types). 70 of the 128 current-scope items never appear in the
  old log at all.
- **Date key**: Phase A (`STATUS.md`, "which date field the demand series is keyed on")
  found the series was keyed on `createDate` project-wide and recommended re-keying on
  `forecast_date` (the contractual delivery date) for inventory-timing purposes; Phase B1
  adopted this. Every downstream script since (`item_level_reconciliation.py`,
  `task3_conditional_item_policy.py`, `backtest_rekeyed.py`) uses the `forecast_date`-keyed
  series; the old forward-test log does not.
- **Model**: the project's adopted approach (`STATUS.md` Phase 2, locked 2026-09-02) is
  Combination forecasting (equal-weight mean of the six candidate models), and for item-level
  forecasting specifically (`STATUS.md` Phase B3), Top-down allocation of the Type-level
  Combination forecast by each item's historical share of its Type. The old log contains neither
  — only the six individual models scored separately.

**Confidence: high** that all three mismatches are real — each is a direct file/code read, not
an inference (old log's own `itemcode` column, `data_cutoff_date`/`model` columns, and
`src/forward_test.py`'s own source, all inspected directly).

**Action taken**: copied (not deleted) `forward_test_log.csv` and `forward_test_scored.csv` to
`output/summary/archive/forward_test_log_58items_createDate_superseded_2026-09-04.csv` and
`..._scored_...csv`, with a full explanation written to
`output/summary/archive/SUPERSEDED_forward_test_log_58items_createDate_README.txt` (the three

was never scored). The originals were then removed from `output/summary/` so nothing running

## 2. Data cutoff used, and why

**Used: the existing frozen pull** (`output/data/processed_full_category_sales_monthly_
forecastDate.csv`, `snapshot_pull_date` = 2026-09-02 15:52:39, 31 months 2024-01 to 2026-07),
**not a fresh live pull**, even though the database was confirmed reachable and fresh
(`SELECT MAX(createDate)` returned 2026-09-03 when tested directly).

**Reasoning** (this was checked, not assumed): the project's leakage guard
(`src/leakage_guard.py`, `config.yaml` `leakage_guard.min_margin_days: 30`) requires at least 30
days between a fitted window's last month-end and the data's pull date, because Phase A found
`forecast_date`-keyed rows for an already-elapsed calendar month can still be entered/revised
afterward. The existing 2026-09-02 pull's fitted window (ending 2026-07) already clears this by
33 days — reconfirmed directly by calling `leakage_guard.check_window_closed` in
`src/forward_test_v2.py` rather than assuming it still holds (it does; see console log below). A
fresh pull today (2026-09-04) would only widen that margin to 35 days and would **not** unlock
August 2026 as a fittable month, since August's month-end is only 4 days behind today — nowhere
near the 30-day margin. Re-pulling therefore buys no additional fittable history while
introducing a second, undocumented pull-timing baseline alongside the one every other Phase-B/
Task-2/Task-3 output in this project already uses. **Confidence: high** — this is a direct
recomputation (`check_window_closed`, called live), not an estimate.

Console evidence from the actual run (`python src/forward_test_v2.py`):
```
Leakage guard OK: fitted window ends 2026-07, pull_date=2026-09-02 15:52:39, margin=33 days (>= required 30)
date_key=forecastDate, approach=Top-down, 128 scope items, fitted 2024-01 to 2026-07 (31 months), forecasting 6 months ahead: ['2026-08', '2026-09', '2026-10', '2026-11', '2026-12', '2027-01']
113 of 128 scope items have full 31-month history; 8 Types, 2 Categories
```

## 3. Method (reused, not reinvented)

- **Item level (128 rows × 6 horizon)**: `src/item_level_reconciliation.py`'s
  `forecast_all_approaches`'s `"Top-down"` branch, called unmodified, on the 113 of 128 items
  with at least one row of sales history (`build_item_series`/`build_type_series`, also reused
  unmodified). This allocates each Type's Combination forecast to member items by historical qty
  share of the Type over the full 31-month fitting window.
- **The 15 of 128 items with zero sales history anywhere** (`has_any_history=False` in
  `part1_category_scope_all_codes.csv`) get `forecast_qty = 0` for every horizon, computed
  directly (`np.zeros(horizon)`), not routed through the reused function. This is the
  mathematically exact result the same Top-down formula would produce anyway (0 historical qty ÷
  a positive Type total = 0% share ⇒ 0 forecast) — not a placeholder, a guess, or a different
  method; it was only computed directly to avoid feeding an all-zero series into
  Croston/SBA (untested elsewhere in this project) for a result that is 0 either way.
- **Type level (8 rows × 6 horizon)** and **Category level (2 rows × 6 horizon)**: the plain
  Combination forecast (`src/models.py` `combination_forecast` — equal-weight mean of
  Naive/MA3/MA6/MA12/Croston/SBA), fitted directly on the Type's / Category's own monthly qty
  series over the same 31-month window. `build_category_series` is the one genuinely new
  function (`src/forward_test_v2.py`) — `item_level_reconciliation.py` had no Category-level
  equivalent to `build_type_series`; it mirrors that function exactly, one level up, rather than
  modifying the existing tested one.
- All forecasts pass through `np.clip(..., 0, None)` (never negative) — and are additionally
  asserted non-negative before the log is written (raises `ValueError` otherwise), per
  `CONVENTIONS.md`'s "forecasts never negative" invariant.

## 4. Schema — `output/summary/forward_test_log_v2.csv` (828 rows)

Extends `src/forward_test.py`'s original 9-column schema. Kept the original `itemcode` column's
*shape* (one identifier column) rather than splitting it per level, per this task's suggestion;
a new `level` column disambiguates what it holds:

| Column | Meaning |
|---|---|
| `itemcode` | item code (level=Item), Type name (level=Type), or Category name (level=Category) |
| `level` | `"Item"` / `"Type"` / `"Category"` — **new** |
| `category` | the row's Category (always populated) — **new** |
| `type` | the row's Type (populated for Item/Type; empty for Category, which has no single Type) — **new** |
| `forecast_run_date` | date this script ran (2026-09-04) |
| `data_cutoff_date` | the frozen pull's `snapshot_pull_date` date part (2026-09-02) — see §2 |
| `fit_last_month` | last calendar month actually used to fit (2026-07) — **new**; distinct from `data_cutoff_date` since target months are computed from this, not from the raw pull date |
| `model` | `"Top-down_Combination"` (Item rows) or `"Combination"` (Type/Category rows) |
| `config_version` | md5 (12 hex chars) of `config.yaml` at generation time — reused `src/forward_test.config_version()`, not reimplemented |
| `date_key` | `"forecastDate"` — **new**, lets the consistency check verify the series key |
| `scope_hash` | md5 (12 hex chars) of the sorted 128-code scope set — **new** |
| `scope_n_items` | 128 — **new**, human-readable companion to `scope_hash` |
| `horizon` | 1–6 |
| `target_month` | YYYY-MM |
| `forecast_qty` | the point forecast |
| `actual_qty` | **empty for every row** — never fabricated |

A companion file, `output/summary/forward_test_log_v2_metadata.json`, records
`config_version`/`date_key`/`item_level_approach`/`scope_hash`/`scope_n_items` **once** at
file level (plus the fitting-window and leakage-guard detail), so the consistency check does not
need to re-derive them from every row of a large CSV. Both files are produced by
`src/forward_test_v2.py`; `src/forward_test_common.py` holds the shared `compute_scope_hash` /
`load_metadata` / `save_metadata` helpers used by both the generator and the scorer, so the
hashing convention cannot drift between the two scripts.

**Row counts** (all confirmed by direct read of the written CSV, not estimated):

## 5. Consistency check — `src/score_forward_test_v2.py`

Chose to write a **new script**, not modify `src/score_forward_test.py` in place, so the old
script remains available, unmodified, to re-score the archived 58-item log for historical
reference if ever needed — it must never be pointed at the new log (it pulls actuals on
`createDate` and has no consistency check, both wrong for the v2 log).

**New config values added to `config/config.yaml`** (documented inline there, per
`CONVENTIONS.md`'s "no magic numbers... all tunable values belong in config.yaml"):
```yaml
adopted_series_key: "forecastDate"
adopted_item_level_approach: "Top-down"
adopted_scope_file: "output/summary/part1_category_scope_all_codes.csv"
```

**`verify_consistency()`** (`src/score_forward_test_v2.py`) runs before anything else and checks,
against the log's metadata JSON:

1. `config_version` — recomputed live from the CURRENT `config.yaml` (`forward_test.config_version()`)
2. `date_key` — against CURRENT `config.yaml: adopted_series_key`
3. `item_level_approach` — against CURRENT `config.yaml: adopted_item_level_approach`
4. `scope_hash` — recomputed live from the CURRENT `part1_category_scope_all_codes.csv` code set
5. `scope_n_items` — same source

Any mismatch raises `ForwardTestConsistencyError` (`src/forward_test_common.py`) listing **every**
field that mismatched with its recorded-vs-current values, and refuses to score — never a
silent skip or warning-and-continue.

**A second, independent improvement over the old script**: the old `month_is_complete()` only
checked whether today's calendar date has passed a target month's end. For a `forecast_date`-
keyed series this is not sufficient — Phase A found such rows can still be entered/revised after
the calendar month closes. `score_forward_test_v2.py` instead reuses
`leakage_guard.check_window_closed` with the same `min_margin_days=30` the rest of the project's
backtests already enforce, so a target month is only treated as safe to score once the leakage
margin has passed, not merely once the calendar has.

|---|---|---|
| 2026-08 | 2026-09-01 | **2026-09-30** |
| 2026-09 | 2026-10-01 | 2026-10-30 |
| 2026-10 | 2026-11-01 | 2026-11-30 |
| 2026-11 | 2026-12-01 | 2026-12-30 |
| 2026-12 | 2027-01-01 | 2027-01-30 |
| 2027-01 | 2027-02-01 | 2027-03-02 |

**Earliest month, under the rule this rebuild actually enforces: 2026-08, safe to score from
2026-09-30** (confirmed live: as of today, 2026-09-04, `score_forward_test_v2.py` correctly
reports 0 of 6 target months safe yet — see the control run above). Under the OLD, looser
calendar-only rule, 2026-08 would already read as "complete" today (2026-09-04), which is
precisely the gap Task 2's leakage guard was built to close (a `forecast_date`-keyed month can
still be revised for some time after its calendar end) — re-using that guard here for scoring,
not just for backtesting, is a deliberate, documented choice of this rebuild, not an oversight.
